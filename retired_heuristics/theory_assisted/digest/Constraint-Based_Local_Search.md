**Read on:** 2026-06-11

## Problem solved by this source

This is a reference handbook chapter, not a paper targeting one specific problem. It presents the Constraint-Based Local Search (CBLS) framework and its COMET implementation platform. The framework is a general methodology for formulating and solving hard combinatorial optimisation problems via local search, with the equation *LocalSearch = Model + Search* as its central design principle.

Three case studies are worked through in detail: the Progressive Party problem (assign guests to boats over time periods — a combinatorial assignment with capacity and meeting constraints); Car Sequencing (order cars on an assembly line subject to sliding-window capacity constraints); and Scene Allocation (assign shooting days to scenes minimising actor costs, with a cardinality hard constraint). None of these is a scheduling problem with blocking precedence or mode-dependent access conditions. However, the framework itself is problem-agnostic and the case studies demonstrate patterns that apply directly to paper #2's joint assignment + scheduling structure.

## Technique

**Model layer — constraint quintuple M = (X, D, F, R, S).** Decision variables X take values from domains D(x). Objective F is minimised. Constraints are partitioned into required constraints R (hard, always satisfied — typically easy cardinality/flow conditions used to initialise a feasible assignment) and soft constraints S (difficult, expressed as violation degrees v_c(σ) ≥ 0, softened during search). The overall search minimises E(σ, F) + Σ_{c∈S} v_c(σ) subject to v_c(σ) = 0 for all c ∈ R.

**Violation degrees and gradients.** Each constraint exposes a uniform API: `violations()` returns the scalar violation degree v_c(σ); `violations(x)` returns the variable violation ↓_x(σ, V(c)); `getAssignDelta(x, v)` returns the change in violation if x is reassigned to v, i.e., v_c(σ[x/v]) − v_c(σ). Gradients ↑_x(σ, e) and ↓_x(σ, e) (max increase / largest decrease achievable by changing x) are derived inductively from expression structure (Fig. 5). This API is uniform across algebraic, logical, and combinatorial constraints (e.g., `alldifferent`, `knapsack`, `sequence`, `atmost`).

**Search layer — neighborhood selectors and control primitives.** A neighborhood N(σ_k) is a set of assignments reachable by one local move (single-variable reassignment or two-variable swap). The `neighbor(⟨expr⟩, ⟨N⟩) ⟨Body⟩` primitive submits a (quality, closure) pair to a selector without executing the move immediately. `MinNeighborSelector` retains the move with minimum quality measure; `KMinNeighborSelector` retains the top-k. Multiple neighborhoods (e.g., reassignment ∪ swap) are accumulated in the same selector, implementing a composite VND-style exploration in a few lines. Tabu filtering is implemented by simply gating the `neighbor` call on a tabu predicate (e.g., `tabu[x, v] <= it`).

**Invariants for incremental computation.** Invariants are one-way constraints O ← f(I) maintained automatically via a topologically sorted incremental graph G(X ∪ I, A). The `propagate(G, σ, Y)` algorithm (Fig. 20) updates all downstream invariants when a subset Y of decision variables changes. Standard invariants include summation aggregates (O(1) update: σ(x) := σ(x) + σ(y) − σ_l(y)), counting invariants (O(1) update maintaining a count array), and compiled expression invariants (Fig. 21, function I: E → X × 2^I). This enables every call to `violations()`, `violations(x)`, and `getAssignDelta(x, v)` to run in O(1) or O(k) where k is the number of affected invariants, making large neighborhood exploration efficient.

**Synthesised search.** COMET can analyse a model's constraint structure and auto-generate a composite neighborhood. For knapsack-structured models it automatically unions single-variable reassignments with pairwise swaps within violated knapsack constraints (the idea from Van Hentenryck [19] in the references). For cardinality/sequence constraints it uses a flow algorithm to initialise a feasible required-constraint assignment, then softens the difficult constraints and runs tabu search. The synthesised procedure matches hand-crafted implementations empirically (Progressive Party, Car Sequencing, Scene Allocation benchmarks).

## What transfers to paper #2

- **Required / soft constraint split for initialisation** — Paper #2 has a natural hard constraint (each aircraft assigned to exactly one position; no two aircraft overlap at the same position with gap ≥ ε; job chain precedences). These can serve as R, initialised greedily or via a simple feasible-flow assignment. The access-mode constraints (Modes A/B/C) and the objective terms (makespan, delay, movements) are naturally soft. The CBLS quintuple M = (X, D, F, R, S) maps cleanly: X = {π(r), s_j}, R = {assignment uniqueness, non-overlap, precedence chain, earliest-start}, S = {Mode-A/B/C feasibility for each access instant, delay penalties, movement count}. Cost: moderate (defining violation degrees for Mode-B/C constraints requires careful algebra but follows the constraint conversion rules in Fig. 4 directly). Risk: low; the framework is generic.

- **getAssignDelta as the core move-evaluation oracle** — For paper #2, the key local moves are: (1) reassign aircraft r to a different position π'(r), (2) shift the start time s_j of a job by Δ. For both, the violation delta can be computed incrementally if the right invariants are maintained (e.g., a count of Mode-C conflicts per blocking arc). The CBLS `getAssignDelta(x, v)` pattern, implemented via invariants, avoids re-evaluating the entire schedule from scratch on each candidate move. This is the single most impactful implementation pattern for paper #2's local search inner loop. Cost: high (requires designing the invariant graph for job start times and position assignments, including the interaction between κ_j and access mode classification). Risk: medium — the invariant update logic for the blocking-arc Mode-A/B/C conditions is non-trivial because a position reassignment can change the mode of multiple access instants simultaneously.

- **Composite neighborhood: reassignment ∪ time-shift ∪ swap** — The CBLS framework makes it trivial to accumulate multiple neighborhoods in one selector (Fig. 12, the progressive party composite). For paper #2 a natural composite is: (N1) reassign one aircraft to a different position, (N2) shift one job's start time forward or backward by δ-granularity steps, (N3) swap the position assignments of two aircraft. The selector picks the best move across all three by quality (violation delta), implementing VND without explicit alternation logic. Cost: moderate once the delta functions are in place. Risk: low.

- **Tabu filter on position assignments** — The progressive party and car sequencing examples both use a simple tabu array indexed by (variable, value) with tenure ≈ 20 iterations and dynamic tenure adjustment (tenure − 1 if improving, tenure + 1 if stagnating, lines 26–27 of Fig. 12). For paper #2's position assignment variables {π(r)}, an analogous tabu[r, p] array prevents revisiting recently abandoned (aircraft, position) pairs. Cost: trivial (one 2-D integer array). Risk: none.

- **Diversification via restart with random perturbation** — The car sequencing synthesised search (Fig. 16) and scene allocation manual search (Fig. 18) both implement diversification by detecting a `stable` counter threshold (500 iterations without improvement) and performing a random subset permutation/reassignment of variables. For paper #2, when the local search stagnates, randomly reassigning a subset of aircraft to positions (while maintaining hard constraint R feasibility) provides diversification. Cost: low. Risk: low.

- **Violation-weighted soft constraint sum as proxy objective** — The CBLS model objective min E(σ, F) + Σ v_c(σ) combines true objective and violations. For paper #2 during the feasibility phase (finding Mode-A/B/C-feasible schedules), one can drive the search purely by Σ v_c(σ) over the Mode constraints, then switch to optimising F = W^M·m + W^D·Σv^D_r + W^S·n once feasibility is achieved. This two-phase strategy (infeasibility → feasibility → optimality) is standard in CBLS and directly applicable. Cost: trivial (a flag in the objective evaluation). Risk: low.

- **Counting invariant for movement count n** — The movement count n = total Mode-B + Mode-C events is precisely a summation over access instants, which is a counting invariant in CBLS terms (Example 10, the `count(y)` invariant). Maintained incrementally, it can serve as the O(1)-update component of the objective function. Cost: medium (must define the access-instant membership function correctly). Risk: medium — the classification of an access instant into Mode A/B/C depends on the relative timing of two aircraft, making the update non-local.

- **Semi-greedy selector (KMinNeighborSelector with k=2 or 3)** — The scene allocation generated search uses `selectMin[3]` (top-3 selector, line 13 of Fig. 18) to introduce randomness while retaining quality guidance. This is exactly the BR-GRASP randomisation mechanism discussed in the GRASP digest, implemented here at the selector level rather than the construction level. For paper #2's local search phase, using a KMinNeighborSelector avoids the pure-greedy trap without requiring a full GRASP outer loop. Cost: trivial (a parameter). Risk: none.

## What does NOT transfer

- **COMET platform dependency** — The chapter's code examples are written in COMET, a specialised object-oriented language. Paper #2's implementation is in Python. The CBLS *concepts* (invariants, violation degrees, gradient-based delta evaluation, neighborhood selectors) transfer cleanly, but the COMET API cannot be used directly. The concepts must be re-implemented from scratch in Python.

- **Synthesised search generation** — COMET's automatic synthesis of search procedures from model analysis (Sections "Progressive Party" synthesised search, Fig. 13 and 16) requires the COMET model analysis infrastructure. This meta-level capability is not transferable without the platform.

- **Scene allocation and progressive party specifics** — The knapsack and `alldifferent` constraint structures of those case studies do not appear in paper #2. The specific neighborhoods designed around those constraints (swapping guests in the same knapsack constraint, etc.) do not transfer.

- **Continuous / set / path / tree variable extensions** — The chapter mentions extensions to set, path, and tree variables [12, 22]. Paper #2 uses only integer variables (position assignments, job start times), so these extensions are irrelevant.

- **Constraint hardness classification via cardinality tightness** — The car sequencing analysis that detects whether the `atmost(demand, line)` constraint is tight (a bijection), and uses this to restrict neighbourhoods to feasibility-preserving swaps, is specific to bijective cardinality constraints. Paper #2's hard constraints are not bijective in that sense.

## Verdict for theory_assisted

**Priority:** High

**Rationale:** The CBLS framework provides the most operationally precise vocabulary for implementing the local search phase of paper #2's solver. The key insight — that every constraint must expose `violations()`, `violations(x)`, and `getAssignDelta(x, v)` as O(1) incremental operations maintained by an invariant graph — directly addresses the central implementation bottleneck of paper #2: evaluating candidate moves over the blocking-arc access-mode conditions without recomputing the full schedule. The required/soft split maps exactly to paper #2's hard (non-overlap, precedence, earliest-start) versus difficult (Mode-A/B/C access, delay, movements) structure. The composite neighborhood pattern, tabu filtering, and violation-weighted two-phase objective are all directly transferable with low implementation cost. The main transfer risk is engineering the invariant update logic for the Mode-A/B/C classification, which is more complex than the chapter's examples (alldifferent, knapsack, sequence) because it involves time-ordering interactions between two different aircraft.
